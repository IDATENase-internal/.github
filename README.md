# .github（共通ルール）

この org のリポジトリで共通に使う、GitHub のテンプレートを置くリポジトリです。

| ファイル | 役割 |
|---|---|
| `pull_request_template.md` | PR を作るとき、本文に自動で入る |
| `ISSUE_TEMPLATE/` | Issue を作る画面で、4 種類のフォーム（機能実装・改善 / 不具合修正 / 調査・検証 / その他）から選ぶ。白紙の Issue は作れない |
| `workflow-templates/` | 各リポジトリの Actions →「New workflow」から追加できる CI（Self Review Check） |

## どのリポジトリに効くか

- Issue と PR のテンプレートを org 全体の既定として効かせるには、このリポジトリが **public** である必要があります（GitHub の仕様）。そのため、ここに置くファイルはすべて公開される前提で書きます。顧客名、社内の URL、案件固有の情報は書かないでください。
- 自分の `.github/ISSUE_TEMPLATE/` や PR テンプレートを持つリポジトリでは、そちらが優先され、ここのテンプレートは使われません。案件ごとに項目を変えたい場合は、ここのファイルをそのリポジトリにコピーして書き換えてください。
- `workflow-templates/` は、このリポジトリが private のままでも、org の private リポジトリから使えます。

## ラベル

Issue フォームは次のラベルを付けます。リポジトリにそのラベルがないときは、ラベルが付かないだけで Issue は作れます。

| フォーム | ラベル |
|---|---|
| 機能実装・改善 | `enhancement`（GitHub が最初から用意している） |
| 不具合修正 | `bug`（GitHub が最初から用意している） |
| 調査・検証 | `investigation`（各リポジトリで作る） |
| その他 | `task`（各リポジトリで作る） |

## Self Review Check の使い方

1. リポジトリの Actions →「New workflow」で「Self Review Check」を選んで追加する。
2. PR 本文の「AI によるセルフレビュー（`/code-review` など）を実施し…」にチェックがないと、このチェックが失敗します。ドラフト PR と、`staging` / `develop` からの昇格 PR は対象外です。
3. マージを止めたい場合は、ブランチ保護（またはルールセット）でこのチェックを必須にしてください。

## テンプレートの考え方

- **★ の欄だけ必須**。ほかは当てはまらなければ消してよい形にして、書く負担を減らしています。
- **人しか知らないことを聞く**。「どこで確かめたか」「マージ後に必要な作業」「影響の大きい変更か」「顧客データを含むか」など。型チェックのような機械的な確認は、CI や CLAUDE.md / AGENTS.md に書きます。
- **期限と優先度は Issue に書かない**。GitHub Projects のフィールドで管理し、二重管理にしません。
